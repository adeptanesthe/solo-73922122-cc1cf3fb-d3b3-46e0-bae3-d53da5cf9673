# 转写验收 · 说话人配对核验

一个用 Flask 做的会议字幕转写验收页：上传**人工稿**与**识别稿**两份 JSON，页面求出全场的**最少错误**说话人一对一配对，并逐词列出多词、漏词、替换及时间点。审校员可以锁定或撤销配对，每次重算都只展示与最新有效锁定相符的评分与错词。

## 快速启动

```bash
docker compose up --build
```

打开 <http://localhost:8000>。首次构建会安装 Flask / gunicorn / NumPy；容器带健康检查，`GET /healthz` 返回 `{"status":"ok"}`。停止用 `docker compose down`。

> 本机没有 Docker 时，可用 Python 3.11+ 直接运行：
>
> ```bash
> python3 -m pip install -r requirements-dev.txt
> python3 -m flask --app wsgi run --port 8000
> ```

## 怎么用

1. 在页面顶部选择两份 JSON（或用「载入示例稿」按钮直接载入仓库里的 `samples/`）。
2. 页面显示：最少错误总数、词错率（错误数 ÷ 人工稿词数）、替换/漏词/多词构成、每对说话人的明细。
3. 「锁定此配对」把某个配对固定下来；其余说话人仍按最少错误重新分配。「撤销锁定」恢复自由配对。
4. 若锁定会与已有锁定冲突（同一个识别说话人被锁给两个人），页面提示原因，**保留原锁定**，不会写入无效状态。
5. 错词表按时间排序，每行给出类型、配对、人工词与识别词及各自的毫秒时间。

## 输入格式

每份稿件是词数组，或 `{"words": [...]}`：

```json
[
  {"word": "各位", "time_ms": 800, "speaker": "S1"},
  {"word": "早上好", "time_ms": 1160, "speaker": "S1"}
]
```

- `word` 必填且非空；`time_ms` 必填、非负整数毫秒；`speaker` 必填，可写成字符串或数字。
- 兼容别名：`text`、`start_ms` / `start` / `timestamp_ms`、`speaker_id`。
- 每稿最多 **6000 词、8 位说话人**；人工稿必须非空，识别稿允许为空（此时人工稿全部计漏词）。
- 稿件按时间稳定排序；同毫秒的词保留上传顺序。
- 上传限制为每个文件 4 MB，必须是 UTF-8 JSON。

## 评分口径

- **一对一对齐**：一个识别说话人最多配一位人工说话人，反之亦然。
- **按时间顺序对词**：同一对里的词按时间顺序做编辑距离；只有两侧时间相差 **≤ 500 ms** 才允许对齐成匹配或替换。
- **一次一处**：替换、删除（漏词）、插入（多词）各计 1 次错误。
- **全场最少错误**：遍历所有一对一配对（锁定项必须保留），取总错误最少者。未配对的人工说话人每个词计漏词，未配对的识别说话人每个词计多词。平局时优先更完整的配对，再按说话人编号稳定排序。
- **词错率** = 最少错误数 ÷ 人工稿词数。
- 编辑距离相同分数时，优先总时间偏差更小的对齐，使错词时间更贴近人工稿。

## 内存与性能

评分使用滚动行（`O(m)`），回溯使用 Hirschberg 分治（`O(n + m)` 额外内存），不会建 `n × m` 矩阵。全量 6000 词、8 对 8 的实测峰值额外内存约 1–2 MB，规模随总词数线性增长。代价是回溯要多跑几遍滚动行：单对 6000×6000 的最坏情况在本机约 20 秒，页面在 gunicorn `--timeout 120` 内完成。

每次上传只计算一遍不依赖锁定的 8×8 配对代价矩阵；之后每次锁定/撤销重算只重跑配对动态规划和所需配对的对齐。实测 8 人 × 750 词（共 6000 词）的一份稿件：上传首次评分约 6–7 秒，锁定后重算约 3 秒。

## 实现结构

```
app/engine.py        校验、配对、对齐、结果组装（与 Flask 无关）
app/web.py           路由、会话状态、不可变结果快照、锁定冲突处理
app/templates/       页面模板（无 JavaScript 也能完成全部操作）
app/static/          样式与仅作增强的脚本
samples/             两组可直接演示配对核验的稿件
tests/test_app.py    40 个 pytest 用例
Dockerfile           python:3.12-slim + gunicorn，非 root 运行
docker-compose.yml   端口 8000，健康检查
```

页面的锁按钮、手动锁定/撤销表单都是普通 HTML 表单；JavaScript 只额外做文件大小预检和按需拉取 JSON 视图（`GET /api/result`）。POST 会校验 `Origin`/`Referer` 同源。

会话数据保存在进程内存中，所以 Compose 用**单 worker + 4 线程**：多个 worker 之间不共享会话。这对单机验收工具足够；要横向扩展需把会话落到外部存储。

## 示例稿

| 文件 | 演示点 | 期望结果 |
| --- | --- | --- |
| `samples/meeting_ref.json` / `meeting_hyp.json` | 3 位人工说话人对 4 位识别说话人，识别顺序不同；含漏词、替换、多词与一个完全未配对的说话人 | 8 个错误（3 替换、1 漏词、4 多词），词错率 8/53 ≈ 15.09%；配对 S1→T1、S2→T3、S3→T2，T4 未配对 |
| `samples/sparse_ref.json` / `sparse_hyp.json` | 识别词与人工词相差超过 500 ms 无法对齐；人工说话人 S3 未配对 | 6 个错误（4 漏词、2 多词），词错率 6/11 ≈ 54.55% |

在页面上载入 `meeting` 示例后，把 S2 锁给 T1 会立刻看到错误数从 8 升到 83——这就是锁定后按新约束重算的效果。

## 已知限制

- 会话存在进程内存里；进程重启后需要重新上传。
- 回溯为控制内存会重复计算滚动行，6000×6000 的极端单对约需 20 秒；普通会议稿件远低于此。
- 锁定目前按「人工说话人 → 识别说话人」表示，暂不支持标记某个说话人「刻意不配对」（只能靠算法自然产生）。
